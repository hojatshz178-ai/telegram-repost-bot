# ربات خبری نظامی تلگرام — نسخه نهایی 4.0.0

این پروژه یک worker پایتونی برای Railway است که فقط از صفحات عمومی کانال‌های Telegram خبر می‌گیرد، محتوای خبری را با Gemini بازنویسی و طبقه‌بندی می‌کند و نتیجه را در کانال مقصد منتشر می‌کند.

## 1) چهار فایل پروژه

- `bot.py` — هسته کامل ربات
- `requirements.txt` — وابستگی‌ها
- `Procfile` — دستور اجرای Railway Worker
- `README.md` — راهنمای نصب و تنظیم

## 2) تنظیمات Railway

### متغیرهای الزامی

| Variable | توضیح |
|---|---|
| `BOT_TOKEN` | توکن BotFather. این مقدار را داخل کد قرار نده. |
| `TARGET_CHAT_ID` | کانال مقصد، مثلاً `@khaatshekaan` |
| `GEMINI_API_KEYS` | یک یا چند کلید Gemini با کاما؛ کلیدها را فقط در Railway Variables قرار بده. |
| `SOURCE_CHANNELS` | یوزرنیم کانال‌های عمومی تلگرام با کاما و بدون `@` |

### مدل‌های Gemini

پیش‌فرض نسخه 4:

`gemini-3.5-flash-lite,gemini-3.1-flash-lite`

در صورت نیاز می‌توانی `GEMINI_MODELS` را خودت تعیین کنی. مدل‌های قدیمی 2.0 عمداً در کد پیش‌فرض نیستند؛ Gemini 2.0 Flash-Lite از 1 ژوئن 2026 خاموش شده است.

## 3) نکته بسیار مهم درباره Gemini

چرخش بین API Keyها فقط زمانی واقعاً مفید است که محدودیت بین پروژه‌های مستقل باشد. چند کلید که همگی متعلق به یک پروژه Google هستند الزاماً سهمیه مستقل ایجاد نمی‌کنند.

ربات دیگر روی 404 مدل متوقف نمی‌شود: مدل 404 شده موقتاً از چرخه خارج می‌شود و مدل بعدی امتحان می‌شود. 401/403/429 روی سلامت کلید اثر می‌گذارد و 500/502/503/504 روی سلامت مدل. برای خطاهای موقت backoff محدود استفاده می‌شود.

خروجی Gemini با JSON Schema اجباری درخواست می‌شود و بعد از دریافت، در خود Python نیز type و محدوده‌ها اعتبارسنجی می‌شوند. بنابراین مقدار رشته‌ای مثل `"false"` دیگر به اشتباه True محسوب نمی‌شود.

## 4) Railway Volume

برای نگهداری صف، شناسه پست‌های پردازش‌شده، hash پست‌ها، dedup و وضعیت retry یک Volume بساز:

1. Railway → Worker
2. New → Volume
3. Mount Path: `/data`
4. Deploy

بدون Volume، state بعد از restart/redeploy پایدار نمی‌ماند.

## 5) فقط یک Worker/Replica

این برنامه state را به صورت فایل اتمیک نگه می‌دارد و برای چند worker همزمان طراحی نشده است. تعداد replica را روی **1** نگه دار. اجرای همزمان دو worker می‌تواند باعث دوباره‌فرستادن خبر یا race روی state شود.

## 6) رفع خطاهای رسانه

- عکس برای upload مستقیم حداکثر 10MB در نظر گرفته می‌شود.
- ویدئو حداکثر 50MB در نظر گرفته می‌شود.
- نوع واقعی فایل با magic bytes و Content-Type بررسی می‌شود.
- اگر upload مستقیم رسانه شکست بخورد، URL رسانه به Telegram داده می‌شود.
- اگر رسانه ارسال شد ولی متن تکمیلی طولانی شکست خورد، رسانه دوباره ارسال نمی‌شود و duplicate ایجاد نمی‌شود.

## 7) منطق صف شب

بین 00:00 تا 08:00، خبرهای غیر فوری وارد صف می‌شوند. خبر فوری می‌تواند همان لحظه منتشر شود.

مهم‌ترین اصلاح نسخه 4 این است که آیتم صف **قبل از ارسال حذف نمی‌شود**. ابتدا Telegram باید انتشار موفق را تأیید کند؛ فقط بعد از موفقیت از صف حذف و timestamp انتشار ثبت می‌شود. در صورت خطا، آیتم با retry باقی می‌ماند.

## 8) منطق dedup و ویرایش پست

برای هر پست علاوه بر UID، hash محتوا ذخیره می‌شود. بنابراین اگر یک کانال همان message ID را ویرایش کند، در صورت فعال بودن `REPROCESS_EDITED_POSTS` تغییر تشخیص داده می‌شود.

امضای خبر فقط پس از انتشار موفق به عنوان published ثبت می‌شود. آیتم صرفاً queued شده با published اشتباه نمی‌شود.

## 9) burst

ربات دیگر صرفاً به دلیل اینکه مثلاً 4 پست در یک polling دیده شده‌اند همه را یکی نمی‌کند. قبل از burst، شباهت واژگانی پیام‌ها بررسی می‌شود. اگر شباهت کافی نباشد، پست‌ها جداگانه پردازش می‌شوند.

## 10) محدودیت ذاتی روش دریافت

منبع‌خوانی فعلی از `https://t.me/s/<channel>` و HTML عمومی Telegram است؛ بنابراین فقط کانال‌های عمومی قابل‌خواندن هستند. این روش API رسمی دریافت پست‌های کانال‌های دیگر نیست و ممکن است در صورت تغییر HTML تلگرام نیاز به به‌روزرسانی parser داشته باشد.

برای کاهش خطر parser break، اگر پاسخ HTTP 200 باشد ولی هیچ markup مربوط به پست Telegram پیدا نشود، ربات آن را به عنوان وضعیت مشکوک log می‌کند و آن را بی‌دلیل به عنوان «کانال بدون خبر» تفسیر نمی‌کند.

## 11) اولین اجرا

پیش‌فرض `PROCESS_EXISTING_ON_FIRST_RUN=false` است. یعنی پست‌هایی که هنگام اولین bootstrap روی صفحه عمومی دیده می‌شوند به عنوان وضعیت اولیه ثبت می‌شوند و از پست‌های بعدی شروع می‌کند.

اگر می‌خواهی همان پست‌های موجود هم پردازش شوند:

`PROCESS_EXISTING_ON_FIRST_RUN=true`

## 12) اجرای محلی

```bash
pip install -r requirements.txt
python bot.py
```

در Railway فقط همین چهار فایل را deploy کن و Environment Variables را تنظیم کن.

## 13) امنیت

- توکن Telegram و API Keyهای Gemini داخل `bot.py` نیستند.
- کلیدها در لاگ چاپ نمی‌شوند؛ فقط fingerprint کوتاه برای تشخیص داخلی نمایش داده می‌شود.
- متن منبع داخل Gemini به عنوان داده غیرقابل‌اعتماد delimiter شده تا prompt injection از متن خبر، دستورالعمل اصلی را تغییر ندهد.
- متن خروجی پیش از ارسال HTML-escape می‌شود.

## 14) رفتار خطا

### Gemini
- 404 → مدل موقتاً کنار گذاشته و fallback
- 401/403 → کلید موقتاً کنار گذاشته
- 429 → Retry-After در صورت وجود + backoff
- 408/500/502/503/504 → retry محدود
- 400 و خطاهای مشابه → بدون brute-force بی‌فایده، چون معمولاً مشکل payload/config است

### Telegram
- 429 با `retry_after` مدیریت می‌شود.
- خطای شبکه تا چند بار retry می‌شود.
- شکست انتشار باعث گم‌شدن خودکار پست نمی‌شود مگر اینکه سقف retry تنظیم‌شده پر شود.

## 15) نکته عملی

برای ربات خبری پرترافیک، polling پنج‌دقیقه‌ای ممکن است باعث شود تعداد زیادی پست بین دو polling از محدوده صفحه عمومی خارج شوند. برای کاهش این مشکل، `POLL_INTERVAL_SECONDS` را می‌توان کاهش داد؛ اما polling سریع‌تر مصرف شبکه و درخواست‌ها را افزایش می‌دهد.
