# Raptor News Bot — نسخه بازطراحی‌شده

این نسخه برای ساخت یک کانال خبری تمیز و مرجع طراحی شده است؛ هدف این نیست که هر پست منبع فوراً و جداگانه وارد کانال شود. ربات خبرهای جدید را می‌گیرد، مطالب مرتبط با یک رویداد را قبل از انتشار گروه‌بندی می‌کند، با Gemini جمع‌بندی و بازنویسی می‌کند، رسانه را تا حد ممکن حفظ می‌کند، و همه خبرهای عادی را داخل یک صف اولویت‌دار با فاصله **۶۰ تا ۳۰ دقیقه** منتشر می‌کند.

> نکته امنیتی مهم: کلیدهای Gemini را داخل `bot.py` یا GitHub قرار نده. کلیدهایی که در گفتگو یا جای دیگری افشا شده‌اند را بهتر است تعویض کنی و فقط در Railway → Variables قرار بدهی.

## تغییرات اصلی این نسخه

### 1) خبرهای یک واقعه دیگر پشت‌سرهم منتشر نمی‌شوند

اگر یک کانال در مدت کوتاه چند پست درباره یک اتفاق بفرستد، ربات ابتدا پست‌های مرتبط را در یک cluster قرار می‌دهد و آن‌ها را در اختیار Gemini می‌گذارد.

Gemini برای هر cluster حداکثر **۲ خروجی** می‌سازد:

- معمولاً یک جمع‌بندی کامل
- حداکثر دو پست فقط وقتی دو تحول مستقل اما مرتبط وجود داشته باشد

بنابراین جریان‌هایی مثل:

- خبر اولیه
- تصاویر جدید
- جزئیات بیشتر
- واکنش طرف مقابل
- آمار جدید
- ادامه خبر

به صورت پیش‌فرض به یک جمع‌بندی واحد نزدیک می‌شوند، نه ده‌ها پست کوتاه.

### 2) فاصله انتشار استاندارد

قانون انتشار:

| اندازه صف | فاصله |
|---|---:|
| ۰ تا ۳ پست | ۶۰ دقیقه |
| ۴ تا ۸ پست | ۵۰ دقیقه |
| ۹ تا ۱۴ پست | ۴۰ دقیقه |
| ۱۵ پست به بالا | ۳۰ دقیقه |

فاصله **هیچ‌وقت کمتر از ۳۰ دقیقه نمی‌شود**.

حتی خبرهای `urgent` از این حد عبور نمی‌کنند؛ urgent فقط باعث می‌شود خبر در اول صف قرار بگیرد.

### 3) اولویت‌بندی

امتیاز صف ترکیبی از این موارد است:

1. رویداد نظامی / حمله / جنگ / درگیری
2. خبر فوری
3. اهمیت راهبردی
4. ایران
5. سایر خاورمیانه
6. آمریکا / روسیه / چین و سایر قدرت‌های بزرگ
7. سایر نقاط دنیا

در عین حال اخبار اروپا، آسیا، آفریقا و سایر نقاط جهان حذف نمی‌شوند؛ برای جلوگیری از یکنواختی، تکرار یک منطقه پشت سرهم جریمه جزئی می‌شود.

### 4) عکس

اولویت گرفتن عکس:

1. عکس اصلی پست تلگرام
2. `og:image` مقاله
3. تصویر/thumbnail موجود در RSS
4. جستجوی تصویر موضوعی از Wikimedia Commons
5. در صورت شکست همه روش‌ها، خبر بدون عکس منتشر می‌شود

در نسخه قبلی از `source.unsplash.com` استفاده می‌شد؛ این روش قابل اتکا نیست و حذف شده است.

> تصویر fallback موضوعی است و لزوماً عکس همان رویداد نیست. ربات آن را به عنوان «تصویر دقیق صحنه حادثه» معرفی نمی‌کند.

### 5) رسانه اصلی تلگرام

برای پست‌های تلگرام، در صورت وجود عکس یا ویدیو تلاش می‌شود همان رسانه اصلی دوباره در کانال مقصد آپلود شود.

پست‌های مدیا بدون متن هم دیگر به طور خودکار حذف نمی‌شوند.

### 6) سایت و RSS

اگر RSS فقط یک خلاصه کوتاه داشته باشد، ربات در صورت وجود لینک مقاله صفحه اصلی را هم بررسی می‌کند تا:

- `og:image`
- `og:title`
- `og:description`
- زمان انتشار
- متن مقاله

را تا جای ممکن پیدا کند.

### 7) منبع خبر

در خروجی، لینک منبع اصلی حفظ می‌شود تا پست بدون اعتباردهی به منبع منتشر نشود.

### 8) Gemini با ۱۴ کلید

تعداد کلید محدود به عدد خاصی نیست. برای وضعیت فعلی می‌توانی **۱۴ کلید** را در متغیر `GEMINI_API_KEYS` قرار بدهی.

ربات برای هر کلید وضعیت جداگانه نگه می‌دارد:

- آخرین استفاده
- آخرین status
- تعداد خطا
- زمان cooldown

بنابراین کلیدی که 429 یا 401/403 می‌دهد موقتاً کنار گذاشته می‌شود و بیهوده پشت سر هم تست نمی‌شود.

### 9) خطاهای شبکه

موارد زیر باعث از دست رفتن دائمی خبر نمی‌شوند:

- Timeout
- ConnectionError
- DNS/SSL/شبکه
- 429
- 500/502/503/504
- شکست موقت Telegram

اگر پردازش کامل نشود، UID خبر ثبت نمی‌شود و در چرخه بعد دوباره قابل پردازش است.

### 10) State امن

`state.json` با روش:

`temp file → flush → fsync → atomic replace`

ذخیره می‌شود تا قطع ناگهانی فرایند فایل اصلی را خراب نکند.

## متغیرهای Railway

### ضروری

`BOT_TOKEN`

توکن ربات Telegram.

`TARGET_CHAT_ID`

مثلاً:

```text
@your_channel
```

یا chat id مربوط به کانال.

`SOURCE_CHANNELS`

چند کانال با کاما:

```text
channel1,channel2,channel3
```

`SOURCE_WEBSITES`

چند RSS با کاما:

```text
https://example.com/rss,https://example.com/feed
```

`GEMINI_API_KEYS`

کلیدها را با کاما و بدون فاصله اضافه قرار بده:

```text
KEY_01,KEY_02,KEY_03,KEY_04,KEY_05,KEY_06,KEY_07,KEY_08,KEY_09,KEY_10,KEY_11,KEY_12,KEY_13,KEY_14
```

هر `KEY_XX` را با کلید واقعی خودت جایگزین کن.

برای امنیت، خود کلیدها را در فایل پروژه ذخیره نکن.

## متغیرهای اختیاری

`GEMINI_MODEL`

پیش‌فرض:

```text
gemini-3.8-flash
```

`POLL_INTERVAL_SECONDS`

پیش‌فرض:

```text
180
```

یعنی هر ۳ دقیقه منابع بررسی می‌شوند.

`DEDUP_WINDOW_MINUTES`

پیش‌فرض:

```text
360
```

یعنی ۶ ساعت.

`DEDUP_SIMILARITY_THRESHOLD`

پیش‌فرض:

```text
0.82
```

برای جلوگیری از حذف خبرهای صرفاً مشابه، این آستانه محافظه‌کارانه‌تر از نسخه قبلی است.

`EVENT_CLUSTER_WINDOW_MINUTES`

پیش‌فرض:

```text
90
```

یعنی پست‌های نزدیک به هم از نظر زمانی شانس بالاتری برای گروه‌شدن دارند.

`EVENT_MAX_ITEMS_PER_CLUSTER`

پیش‌فرض:

```text
6
```

`EVENT_MAX_OUTPUT_ITEMS`

پیش‌فرض:

```text
2
```

`STATE_FILE`

برای Railway بهتر است روی Volume دائمی باشد. نمونه:

```text
/data/state.json
```

## Railway Volume

چون فایل local در یک سرویس بدون volume دائمی ممکن است بعد از restart/deploy از بین برود، بهتر است یک Volume پایدار متصل کنی و:

```text
STATE_FILE=/data/state.json
```

قرار بده.

اگر `/data` وجود داشته باشد، حتی بدون تنظیم دستی هم پیش‌فرض برنامه روی `/data/state.json` می‌رود.

## requirements.txt

فایل نهایی این پروژه باید دقیقاً شامل dependencyهای استفاده‌شده باشد:

```text
requests>=2.31.0,<3
feedparser>=6.0.10,<7
beautifulsoup4>=4.12.3,<5
tzdata>=2025.2
```

## نکته درباره عکس

هیچ سیستم متنی نمی‌تواند تضمین کند که یک عکس stock دقیقاً همان صحنه یک رویداد واقعی باشد. برای همین این نسخه اولویت را به تصویر خود منبع و `og:image` مقاله می‌دهد و فقط در نبود آن‌ها از fallback موضوعی استفاده می‌کند.

## ساختار انتشار

منطق نهایی تقریباً این است:

```text
Source
  ↓
Fetch
  ↓
Extract text + media + timestamp + source URL
  ↓
Find unprocessed items
  ↓
Cluster related posts of the same event
  ↓
Gemini rewrite + classify + urgency + region
  ↓
Cross-source dedup
  ↓
Select original/source image or Wikimedia fallback
  ↓
Priority Queue
  ↓
Publish every 60 → 50 → 40 → 30 min
```

## قانون مهم پردازش UID

UID فقط بعد از موفقیت کامل پردازش cluster ذخیره می‌شود.

یعنی اگر Gemini یا Telegram موقتاً مشکل داشته باشد:

```text
خبر گم نمی‌شود
```

و در چرخه بعد دوباره قابل پردازش است.

## نکته فنی درباره Telegram

این پروژه همچنان از preview عمومی `t.me/s/<channel>` استفاده می‌کند. این روش برای کانال‌های عمومی مناسب است، اما Telegram در نهایت API رسمی Bot/Client را برای سناریوهای پیچیده‌تر بهتر پشتیبانی می‌کند.

اگر بعداً به MTProto/client رفتی، منطق صف و dedup همین نسخه را می‌توانی نگه داری و فقط لایه دریافت Telegram را عوض کنی.

## نکته درباره زمان

ساعت پیام صبح:

```text
08:00
```

ساعت پیام شب:

```text
00:00
```

به وقت تهران.

اخبار عادی در بازه ۰۰:۰۰ تا ۰۸:۰۰ داخل صف می‌مانند و در روز بعد طبق اولویت منتشر می‌شوند.

## اجرا

```bash
python bot.py
```

قبل از اجرا مطمئن شو:

```text
BOT_TOKEN
TARGET_CHAT_ID
GEMINI_API_KEYS
```

تنظیم هستند و حداقل یک منبع در `SOURCE_CHANNELS` یا `SOURCE_WEBSITES` وجود دارد.
